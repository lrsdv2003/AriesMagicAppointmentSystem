# Secure personnel operations

This feature is local-only until release and hosting gates pass. No existing account/database is reset by application startup. H4 remains inactive. `IdentitySeeder` initializes only Client/Staff/Admin/Owner role definitions using RoleManager and checks failure results; it creates no users or credentials.

## Configuration and account workflow

- `Personnel__PublicOrigin`: reviewed HTTPS origin, for example the existing Aries site origin, with no credentials, path, query or fragment. Never use a request Host header to construct enrollment links.
- `Personnel__InvitationHours`: 1–48, default 24. Applies to new/rotated invitations.
- `Personnel__AdminMayManageStaff`: false by default. Set true only through explicitly approved hosting configuration if Admin delegation is wanted. Owner invitations do not depend on this flag.
- `FeedbackMedia__UploadsEnabled` remains false/absent. Production SQL/SMTP, Data Protection settings and all private mappings remain separately preserved.

Owner Dashboard > Manage personnel accounts: invite Admin or Staff, inspect personnel, resend/rotate pending links, revoke pending invitations, deactivate/reactivate enrolled personnel, revoke sessions or change between Admin/Staff roles. Owner accounts cannot be created/promoted/modified through these actions. Client accounts cannot be promoted by invitations; duplicate existing email is rejected. Admin sees/manages Staff only when explicitly delegated; Staff has no management access. Legacy Admin password-based CreateStaff is retired and cannot create accounts. Legacy Staff email edits are refused; invitation verification must not be bypassed.

Pending accounts are inactive, roleless and passwordless. Only a SHA-256 digest of a 256-bit random enrollment secret is stored, together with role, issuer, expiry and state in Identity UserTokens. SQL application locks serialize bootstrap, issue, activation and management. Role/UserManager operations and audit commit atomically. Link possession verifies the invited mailbox only when delivered through that mailbox; operator fallback must independently verify mailbox ownership before delivery. GET performs no activation; the fragment is removed from browser history and is not sent in GET/referrer logs. CSRF-protected POST validates the single-use secret and Identity password policy before confirming email, assigning the stored role and activating. Invalid submissions do not echo secrets/passwords. Old/rescinded links cannot change the role. A disabled/demoted issuer cannot authorize later activation. Revoked invitation emails remain reserved; they cannot be silently reused or turned into a different account.

Cookie security stamps are validated on every authenticated request (additional database lookup). Deactivation, reactivation, role changes and session revocation rotate stamps. Password reset is unavailable for inactive/unconfirmed users, preventing enrollment bypass. Existing enrolled users retain the standard verified-email password-reset flow. Existing media authorization, financial policies and Client-only registration remain.

## EJ: first Owner after an approved clean setup

The offline utility is `tests/PersonnelOperator`. It is excluded from the IIS publish artifact. Run it only on an authorized Windows operator workstation; do not add a web setup endpoint or install this tool under the website. Build it from the release commit with `dotnet build tests/PersonnelOperator/PersonnelOperator.csproj -c Release`. Provisioning itself never applies migrations.

1. Obtain explicit approval naming the exact target SQL database and intended Owner email; independently verify mailbox ownership using an approved channel. Do not type connection strings or invitation secrets into chat, command arguments, scripts, logs or source files.
2. Use a private operator process with protected environment input. Set `ARIES_OPERATOR_SQL` to the authorized SQL connection, `ARIES_OPERATOR_DATABASE` to the exact approved catalog, and `ARIES_OPERATOR_APPROVAL=APPROVED`. The tool opens SQL and compares the effective database to the approved name, and refuses pending migrations. Keep SQL encryption/certificate validation enabled for hosted connections. Clear these process variables afterward.
3. Invoke `dotnet run --project tests/PersonnelOperator/PersonnelOperator.csproj -c Release --no-build -- roles`. It creates only missing role definitions. Normal Production startup does not create privileged users.
4. Select an existing protected operator-only delivery folder outside source/publish/website roots. Tool rejects broadly accessible Windows folders and never changes ACLs. Set `ARIES_OPERATOR_APPLICATION_ROOT` to the actual application root to exclude, `ARIES_OPERATOR_DELIVERY_FILE` to a new unused absolute filename in that protected folder, `ARIES_OPERATOR_ORIGIN` to the approved HTTPS origin, `ARIES_OPERATOR_EMAIL` to the approved Owner mailbox, `ARIES_OPERATOR_NAME` to the approved name, and `ARIES_OPERATOR_MAILBOX_VERIFIED=VERIFIED` only after step 1. Do not reuse a delivery filename.
5. Invoke the same tool with final argument `bootstrap`. It refuses a database containing Identity users or booking/payment records, including an already pending Owner. A concurrent second bootstrap is rejected. No password is created. Only the private delivery file receives the enrollment URL; console output contains no secret.
6. The authorized operator securely delivers that link to the independently verified recipient. Never paste it into tickets/chat or put it in a public directory. The recipient opens the HTTPS link and chooses their own password. Activation verifies the exact enrollment and grants Owner. The tool's temporary Data Protection provider is ephemeral and never accesses/creates production keys; invitation validation depends on the stored digest, not a portable default key ring.
7. Confirm Owner login and dashboard/personnel access. Protect/expire the delivery file under the approved retention procedure; do not retain plaintext links in source/backups/artifacts. If delivery failed or expired, run `deliver` with the same private inputs and a new delivery filename. For pending Owner it rotates the link; for Admin/Staff it requires the original issuer to remain authorized. The prior link becomes unusable. No credentials are printed.

The web invitation action attempts SMTP. If SMTP is unavailable, the page reports failure and leaves the account inactive; it never displays a token. An operator uses `deliver` after verifying recipient mailbox ownership. Do not call a scanner, SMTP mock or Identity token bypass to activate personnel. Validate actual production email delivery separately before inviting testers.

Private delivery does not bypass global Production SMTP configuration validation. Existing required host/sender/TLS settings must remain valid even when delivery is temporarily unavailable. Owner/operator delivery uses a fixed 24-hour invitation lifetime; web invitations use the configured bounded lifetime.

## Lost or inaccessible only Owner

Do not bootstrap another Owner, promote an Admin, edit SQL password hashes or reset keys. First use the normal verified-mailbox Forgot Password flow for an active Owner. If disabled or credentials are compromised, an authorized recovery operator independently verifies the existing Owner's mailbox, records approval and protects a recovery point. Run the offline tool with the same approved database/email variables and `recover-owner`. It verifies the selected account already has Owner role, invalidates its password/stamp/tokens via the existing recovery service, reactivates that same account with audit, and creates no role/account. Complete the normal verified-email password reset afterward; SMTP/recovery delivery must actually work. If the mailbox or key dependencies are unavailable, stop for separately approved identity/recovery work—there is no public emergency promotion route.

## Controlled clean-database preparation — DO NOT EXECUTE WITHOUT APPROVAL

1. Prefer a new isolated capstone catalog and connection cutover over dropping the current catalog. Record exact old/new database identities, written operator approval, current coordinated SQL/files/config/key recovery and restore evidence. A statement that records are dummy is not permission to erase them. If the hosting plan cannot add a database, obtain provider-supported isolated recovery and a separately approved reset procedure; never auto-drop from this feature.
2. After approval, pause public registration and all writers using the established owned maintenance/worker-stop procedure. Do not rely on a hidden registration button. Keep old application/schema versions from accepting incompatible writes.
3. An approved DBA applies the full current EF migration chain from the exact tested commit to the approved empty catalog with existing authorized credentials. No EnsureDeleted/EnsureCreated, destructive startup flag or synthetic Identity/data fixture. Verify schema and migration history. Initialize only production-approved catalog/configuration records; do not run the integration harness or re-create dummy bookings/payments/passwords.
4. Run role initialization and first-Owner bootstrap above. Enroll Owner, then invite Admin/Staff through the management page. Keep SQL/SMTP/AllowedHosts/private roots/Data Protection identity/repository/dependencies and H4 mode outside source. Preserve existing uploads separately; never delete them as part of Identity setup.
5. Reconcile actual configuration/root/key continuity and current recovery, then explicitly authorize the connection/artifact cutover. Verify login, Client registration, roles, feedback-off, money/cancellation/refund/booking behavior using authorized synthetic records. Reopen normal access only after acceptance. A rollback after new writes must preserve those writes; do not blindly restore an old database.

The same process rebuilds the capstone environment without predetermined privileged passwords. No live reset, migration, account change, add-on purchase or deployment is authorized merely by this document.
