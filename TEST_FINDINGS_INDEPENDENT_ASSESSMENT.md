## Exact changes and limits

- **Payment retries:** an optimistic form-version check against the latest existing payment ID, not a new durable idempotency-key table or receipt-authenticity classifier. It prevents ordinary double-click/retry/refresh/stale-body reinterpretation. A deliberately fresh form can submit a legitimate new installment after review. Reusing a receipt image is still an Owner/OCR advisory decision; the change does not assert one-to-one real-world bank transaction authenticity.
- **Booking retries:** only an exact canonical payload for the same Client, schedule, package, venue, event/contact details and removed inclusions is recognized as the existing active request. A later catalog price change does not create a new intent or rewrite the accepted booking price. Different requests and terminal histories are not globally deduplicated. Final confirmed capacity/buffer validation remains authoritative. A durable operation-key contract covering catalog/inclusion renames and arbitrary payload changes would require separately reviewed persistence design; it is not claimed here.
- **Atomic persistence:** no partial SQL decisions after the injected failures. Filesystem uploads are not database transactions; a failed upload transaction may leave an unreferenced private generated file. No automatic deletion of existing proofs, uploads or backups was added. A file-retention/reconciliation service would need separate approval.
- **Email:** existing outbox delivery is at least once across a crash/unknown SMTP acknowledgement, not a mathematical exactly-once guarantee. Ordinary delivered-item retries do not resend; no email success claim is added to the UI. Existing background-worker settings are unchanged.
- **Venue:** source defaults, local validation and formula tests do not attest effective hosting overrides, real geocoder accuracy, actual driving time or the host's timezone. No origin/configuration change was made. Existing unknown-location failures remain conservative.
- **Deferred:** semantic receipt rejection, automatic financial approval/refund/excess allocation, new serviceability-review policy, a full slot-list UI/contract, new schema and architectural rewrites.
